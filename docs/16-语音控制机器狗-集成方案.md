## 0. 先说人话：这次要接的其实是「两截管子」

机器狗那边已经有一条完整的传送带：**收到一行文字命令 → 迈腿**。串口、Wi-Fi 网页、手机蓝牙，三个口子都在往这条传送带上放命令，走的是同一个入口 `cli_exec()`。

语音那边已经做好另一截管子：**听到声音 → 认出是菜单上的哪句话**。

集成要做的事，就是把两截管子接起来，中间装一个「翻译员」（把听懂的话翻成机器狗的命令）和一个「门卫」（不认识、超范围的话一律不放行）。步态、舵机标定、姿态过渡这些已经验证过的东西，**一行都不用重写**。

### 一个必须先校正的认知

另一边做好的不是「随便说什么都能转成文字」的通用语音识别，而是：

| 部件 | 实际能力 | 比喻 |
|---|---|---|
| WakeNet9（你好小智） | 只认一个唤醒词 | 敲门，敲了才竖耳朵 |
| MultiNet7 中文命令词 | 只认**预先用拼音注册**的几十条固定说法 | 点菜单，菜单外的话听不出来 |
| 312K 参数中文小模型 | 把「中文句子」翻成「点灯动作符号」 | 翻译官，但只学过点灯这一行的话 |

所以它像**点菜单**，不是**听写机**。这一点直接决定路线：一期直接把「菜单」换成机器狗的动作，最快最稳；想听懂「往前挪挪」这种菜单外的话，得重新教那个小模型（重训一轮语料）。

## 2. 核心决策：接在「命令总线」上，不重写动作

```
  麦克风 ─> AFE ─> 唤醒词 ─> MultiNet 命令词 ─> [命令 ID]
                                        ├─(一期) 查表 -> ASCII CLI 命令 ─┐
                                        └─(二期) 中文句子 -> 动作域 LLM ─┤
                                                        动作白名单/限幅 ─┼─> cli_exec() ─> 步态引擎 ─> PCA9685 ─> 8 舵机
  BLE 手机 / Wi-Fi 网页 / 串口 ───────────────────────────────────────────┘
  急停「停」 ─────────────(不排队、不等锁)──────────────> motion_stand()
```

理由：动作切换必经中间态 stand、姿态过渡只插值膝角、11°/拍限速、trim/dir 标定……这些都在 `motion.c`/`gait.c` 里验证过。语音只需「生产一条命令文本」，天然享受和 BLE/网页完全一致的行为与安全。

### 三条路线对比

| | A 命令词直连（**推荐一期**） | B 重训动作域 LLM | C 手机/PC 转发 |
|---|---|---|---|
| 做法 | 搬 ESP-SR 前端，把命令词表换成机器狗动作，查表后调 `cli_exec` | 重造 15 万行机器狗中文语料、改符号表/校验层、重训、过门禁、换新保留集 | 手机系统语音识别 → BLE 发文字命令 |
| 改动量 | 中（新增 3~4 个 C 文件 + 分区/配置） | 大（训练 + 固件解析层重写） | 小（只改 App） |
| 口语覆盖 | 固定 20~40 条 | 菜单外的说法也能懂 | 任意中文（靠手机） |
| 误动作风险 | 极低（查表是确定性的） | 有，靠安全门兜底 | 低 |
| 单板全离线 | 是 | 是 | **否**（依赖手机，可能联网） |
| 建议 | I1~I3 打通整机 | I4 再上 | 只当调试/演示对照通道 |

> **【已拍板】一期走 A（固定命令词直连），B 明确推迟。** 用户 2026-11-15 确认接受「只能说固定命令词」。
> 因此一期**不初始化 `llm_runtime`、不烧 `model.bin`、不动训练仓库**；`llmmodel` 分区留空备用。
> B 保留在 I4 作为纯可选项，不进一期的验收路径，也不作为一期的兜底手段。
> C 只当调试期的对照通道（手机 BLE 发文字命令验证动作表），不算集成成果。

### 有一个坑必须先绕开（历史上真踩过）

`voice-llm` 里那颗 `model.bin` 是**点灯语料**训出来的，只会输出 `<set> <pin> 8 <high>` 这类符号。直接接到机器狗，所有句子都会被解析层拒绝——10-24 那次「语音灯不亮」就是映射表说的语言和模型不匹配（当时是英文映射表配中文模型）。

因此：

- **一期不要初始化 `llm_runtime`**，`llmmodel` 分区留空备用，省 RAM 也省一次踩坑。
- 二期重训后，`model.bin` / `bpe.h` / `symbols.h` 必须**同一批生成**一起换，并改 `command.h` 的符号与校验规则；三者不同批会静默执行错动作，不报错。

## 3. 一期命令词表（初版，拼音注册 → CLI 命令）

MultiNet7 只接受无声调拼音串，中文/阿拉伯数字不能直接注册（已在 `voice-llm` 踩过）。

> 【已拍板】一期只认下面这 **24 条**固定说法，表外一律「没听懂」。表是 I2 注册命令词、录喇叭词、做 50 条口测的唯一依据。
> MultiNet7 上限 128 条，24 条毫无压力；以后要加词只需改表 + 重新生成词库，不用重训模型。
> **I1 实现时补了第 25 条**：原表「停」写成拼音 `ting zhi`（其实是「停止」），说单字「停」可能漏识别；急停漏识别代价太大，故把 `ting zhi` 正名为「停止」，另注册单音节 `ting` 给「停」。单音节词误触发率待 I2 口测验证，不达标就删掉这一条。
> 表里 **# 是序号，不是固件注册 id**（急停别名插在中间）；固件以 `voice list` 打印的 id 为准。
> **I2 实现时按代码实测修正了两处错误映射**，见下表「后退 / 站好 / 站起来」三行。

| # | 说的话 | 注册拼音 | 映射到的 CLI | 备注 |
|---|---|---|---|---|

### 3.1 安全门（查表之后、`cli_exec` 之前，必做）

1. **白名单**：命令必须在上表内；表外一律拒绝并播「没听懂」。
2. **参数限幅**：速度 0~100、周期 800~3000 等沿用 `console.c` 的严格解析（不能用 `atoi` 判合法性）。
3. **状态检查**：姿态过渡期间的新动作交给 `motion` 已有的「中间态 stand + 站稳双条件」机制，不要另写一套。
4. **急停直通**：「停」不进队列、不拿 `cli_exec` 的 2.5 s 执行锁，直接 `motion_stand()`；运动中、播报中、任何状态都优先响应。
5. **行走超时**：语音触发的行走默认 **5 秒自动 `stand`**，避免「喊一声走就一直走、喊停没听见」。后续可加带时长的命令词覆盖。
6. **仲裁与可追溯**：语音 / BLE / 网页 / 串口「最新生效」，但 `stop` 类最高；每条命令打 `source` 标记写日志，方便排查「到底是谁让它动的」。BLE 心跳断连 2.5 s 自动 stand 保留。

### 3.2 为什么 detect 任务里不能直接调 `cli_exec()`

AFE 的 `feed`/`fetch` 是连续音频流，停一拍就丢帧；而 `cli_exec` 可能等 2.5 s 执行锁。正确做法是两级：

```
feed_task (prio5, core0)   I2S -> AFE，只搬运
detect_task (prio5, core0) AFE -> 唤醒/命令词，命中只把 command_id 投进队列（0 超时）
voice_cmd_task (prio4, core0) 出队 -> 白名单 -> cli_exec() 或 motion_stand() -> 播报
```

队列长 1 + `xQueueOverwrite`：连续口误时只保留最新一条，不堆积过期动作。

### 3.3 【已拍板】唤醒词与喇叭回复

**唤醒词：沿用「你好小智」。** 语音工程 `sdkconfig` 里 `CONFIG_SR_WN_WN9_NIHAOXIAOZHI_TTS=y` 就是它，免费、已跑通，直接照搬配置即可，不需要乐鑫定制词，也没有费用与周期。唤醒后的提示音「我在」也现成。

**喇叭回复：要。** 但**不用真人录音**，现成脚本 `E:\esp32-tools\projects\voice-llm\tools\gen_voice_clips.py` 用 edge-tts（`zh-CN-XiaoxiaoNeural`）合成 24 kHz / 16 bit 单声道片段，拼成 `voice_clips.bin`。缓存 `E:\esp32-tools\tts-cache` 里已有 23 段，重跑不重复联网。

**推荐 I2 先上「最小档」：零新增录音，直接用现成 4 段通用词。** 用户要的是「狗有反应」，不是逐条复述动作；短回复还更省 flash、更不容易被自己听见。

| 用途 | 播什么 | 词库片段 | 来源 |
|---|---|---|---|
| 唤醒应答 | 「我在」 | `VC_HERE` | 现成 |
| 动作确认 | 「好的」 | `VC_OK` | 现成 |
| 急停 | 「已停止」 | `VC_STOPPED` | 现成 |
| 表外 / 没听清 | 「没听懂」 | `VC_NOPE` | 现成 |

**增强档（可选，等 I3 稳定后再说）**：想听「好的，前进」这种复述，就用 `gen_voice_clips.py` 新增约 14 段动作词（前进 / 后退 / 快跑 / 左转 / 右转 / 直走 / 站好 / 蹲下 / 趴下 / 握手 / 挥手 / 演示 / 快一点 / 慢一点），首次生成需联网，之后走缓存离线可复现。

- 播报走 `mouth_say_seq()` 拼接（最多 8 段）；最小档每次只发 1 段，增强档「好的 + 动作词」2 段。
- 体积：现词库 559 KB / 23 段。**最小档不增 flash**；增强档 +14 段约 +340 KB。词库由 `EMBED_FILES` 落在 `.rodata`，播放时从 flash mmap 流式读，**不占内部 RAM**——在只有一块板、片内 RAM 紧张的前提下这点很重要。
- 若走增强档，`voice_clips.h` 的 enum 顺序必须与脚本 `CLIPS` 列表严格一致，`clips_init()` 会在启动时校验；不同步会静默播错话。三处一起改：脚本 `CLIPS`、头文件 enum、`voice_clips.c` 的 `k_names[]`。
- 半双工闭麦（`mouth_gate_closed()` + 播完 300 ms 尾巴）原样沿用，否则喇叭说的「好的」会被自己听见、反复触发。

5. 以上都不够 → 结论写进 I0 报告，暂停合壳；此时才讨论另购第二块板或换更大片内 RAM 的芯片。

> 注意：PSRAM 能分担音频缓冲，但 AFE 实例本身要片内 SRAM；`status` 里那 8.5 MB 再大也补不了片内不足，阶梯里没有「多开点 PSRAM」这一项。
>
> **⭐ 判据口径修正（I1 上板实测后，2026-11-15）**：原写法「AFE 建好后最大连续块 < 60 KB 就关 BLE」把**准入条件**和**运行余量**混为一谈。实测 AFE 创建前最大连续块 88~104 KB > 60 KB，引擎一次就建成功；创建后掉到 31 KB 是 MultiNet 一次性大分配造成的**碎片化**，全局历史最低 `free=39,828 B` 也出现在 MultiNet 建立瞬间（早于 AFE），此后再未复现。判定应看「建前最大连续块」+「长时间运行是否重启 / free 是否持续下降」。I1 两者都过 ⇒ **保留 BLE，暂不执行第 2 级**；I2 起改以「运行时 free < 60 KB 或出现重启 / OOM / 播报失败」为触发条件，真识别与运动同时发生若重启，立即关 BLE。

## 13. 「喇叭没声、狗也不动」的定位（2026-11-15 傍晚）

用户报告两件事，性质完全不同：

### 13.1 狗不动 = I1 的安全边界，不是故障

I1 阶段「只装耳朵和嘴，先把手绑起来」。第二轮日志里用户喊的「前进」已被正确翻译成 `walk 50`，但闸门挡住没执行，日志逐条标注 `【I1 只记录，未执行】`。**放行需进 I2**（命令映射 + 安全门 + 急停直通 + 5 s 行走超时），且按项目铁律必须**四脚悬空逐动作验**。

### 13.2 喇叭没声 = 板外硬件，固件无责

逐项证据（现场 `voice say 20` + `voice` 状态）：

| 检查 | 结果 |
|---|---|
| 播报命令 | `已播报片段 20 (here)`，`[ear] 闭麦` 735 ms 后 `[ear] 开麦` |
| I2S TX 计数 | `喇叭 mouth: idle bytes=407088 errors=0 last=ESP_OK queue=0`（持续推流、零错误） |

| 原工程判据 | README：「TX 全速但没声 → 查 MAX98357 VIN/GND/GAIN 和喇叭线」；「`TX is SLOW` 才是 DMA/驱动问题」。本次 bytes 正常增长、errors=0，属前者 |

`mouth.c` 自带的 `mouth_selftest()` 也写着同一句："A silent speaker with a clean log means wiring or amp, not code"。**不需要改代码、不需要重编译。**

### 13.3 排查清单（按可能性排序）

1. **功放/扬声器到底接了没有**——上一步用户只确认「麦克风接好了」，喇叭侧可能压根没接。
2. **VIN 供电与共地**：MAX98357 VIN 接 3V3 或 5V 均可，但 GND 必须与 ESP32、麦克风共地；带载不足会掉压静音（历史「8 舵机全不动」同因）。
3. **扬声器接法**：OUTP / OUTN 两根线直连喇叭，是 BTL 差分输出，**任一脚都不能接 GND**；喇叭 4~8 Ω。先用手机/其他音源单独确认喇叭本体是好的。
4. **信号线**：BCLK→GPIO 15、LRC→GPIO 16、DIN→GPIO 18；别和麦克风 5/6/7 混。
5. **GAIN / SD 悬空**（原工程验证过的配置）；SD 若被接到 GND 等于关断，接高电平会切到右声道（代码已把单声道复制到两个 slot，两边都能出声）。
6. 现场辅助：`voice say 20` 播「我在」；如需长时间连续音便于量线，可再加 `voice tone`（尚未实现）。

### 13.4 对 I2 的影响

**不阻塞。** 狗动起来本身就是最直观的反馈，比喇叭更明显；喇叭可回头再修。

## 14. I2：语音驱动动作（2026-11-15，代码 + 上板 + 真语音行走验收通过）

### 14.1 范围

用户拍板「喇叭接了但不响；**先不管喇叭，先让狗动起来**」。喇叭从 I2 关键路径移出，保留为独立硬件待办（§13）。I2 只做「识别结果 → 安全门 → `cli_exec()` → 步态」，不重写任何步态代码。

### 14.2 复核时发现方案里两处错误映射（已修，其中一处是危险误动作）

| 词 | 原方案映射 | 实测 | 修正 |
|---|---|---|---|
| 后退 | `walk -50` | `execute_pending()` 里 `if (s_req_speed >= 0) motion_set_speed(...)`，且 `motion_set_speed()` 把负值夹成 0 → **负速度被忽略，会按当前速度继续前进**，喊后退却往前冲 | 改为 `UNSUPPORTED`，识别到明确拒绝并播「没听懂」。现有步态层没有后退能力，留到单独一期 |
| 站好 / 站起来 | `stand` | 命令表里**没有独立的 `stand` 命令**，站立由 `cmd_pose` 的 `pose stand` 提供 → 会得到「未知命令」，识别成功却零动作 | 改为 `pose stand` |

> 这两处是「照文档接线就会错」的坑，靠 `voice list` 与上板代码复核抓出来的。

### 14.3 四道安全门（`firmware/main/voice.c`）

1. **白名单**：只有 `k_cmds[]` 登记过的 id / CLI 文本能执行；表外 id 直接拒绝。命令文本全是**编译期常量**，不含任何用户输入字符串，天然限幅。
2. **运行时放行开关 `s_exec`，上电默认 0（只记录）**。烧录后不会立刻动腿，必须人工 `voice exec on`；`exec off` 瞬间立即 `motion_stand()`。
3. **急停直通**：「停 / 停下 / 别动 / 停止」四条别名在 **detect 任务里直接 `motion_stand()`**，不进队列、不拿 `cli_exec` 的 2.5 s 执行锁，任何状态（含 exec=off）都有效。事件带 `stopped` 标志，cmd 任务只补计数与播报，不重复动作。
4. **5 s 行走超时**：`walk/trot/left/right/straight/demo` 触发后自动站定，新命令续期；姿态类撤掉计时。
   - 一个隐蔽坑已堵：**参数类命令（speed/stride/meminfo）不改 deadline**，否则走路时喊「快一点」会把自动停悄悄取消，狗就一直走。
   - 已知抖动：cmd 任务若正阻塞在 `cli_exec`，超时最多晚 2.5 s 生效。

### 14.8 现场三坑（排查顺序，别再重复踩）

1. **「日志全对但腿不动」= 舵机 5 V 没电**。本轮真因是**充电宝断电**，恢复供电后立刻能动。`pcadiag` 全绿（MODE1=0x21 / SLEEP=0 / MODE2=0x04 / PRESCALE=121→50.03 Hz / CH0 ON=0 OFF=285→1392 µs）只能证明 I2C 与 PWM 输出级正常，**证明不了 V+ 有电**；先量舵机红线带载电压、看充电宝开关与指示灯。
2. **【已于 11-16 09:30 修复】旧版每次 USB 拔插、断电、重启会把 `exec` 复位回 0**（当时是安全设计，故意不写 NVS）。用户「插回去又不动了」即此因：当时 `唤醒=2 命中=3` 说明喊得准，只是闸门复位。**现固件 `voice.c` 上电默认 `s_exec=1 / s_muted=0`，两次重启复验均自动放行**（见头部 v1.9 补记）⇒ **重启不需要再开闸**。现在若读到 `exec=0`，只可能是有人手动 `voice exec off`，用 `voice exec on` 或手机 App 的「语音控制 · 安全开关」恢复。
3. **USB 幽灵设备**：插充电宝时 USB 重枚举，pyserial `comports()` 返回 `[]` 或 `PermissionError(13)`，但设备管理器仍见 `USB\VID_303A&PID_1001`。物理拔插标 `USB` 的口即恢复，不是固件问题。

### 14.9 当前遗留（2026-11-16 更新）

- ✅ **喇叭已修复**：根因是 MAX98357 `VIN` 接在 ESP32 板 `5V` 脚（防倒灌二极管，USB 供电时实测仅 0.37 V），改接**舵机 5V / PCA9685 `V+`**（4 V+）后出声；上电 `mute=0`，无需手动 `voice mute off`。播报闭麦 0.7 s 会吞掉紧跟的命令词 ⇒ 唤醒后要等「我在」播完 + 半秒再说命令（§14.7 实测）。
- ✅ **`cli_out` 回话残留已修**（v2.0）：`voice.c` 在 `cli_exec()` 前清空 `s_exec_out`，BLE / App 不再显示上一条命令的旧文字（原先 `pose crouch/stand` 的 `rc=0` 但回话串台）。
- ✅ **安卓 App「后退」误动作已禁用**（v2.0）：原按钮发 `walk -50`，与语音词表第 2 条同款错误（负速度被跳过后继续前进）；现改为点击只提示「未开放」，不发命令。
- ✅ **App 新增语音安全开关**（v2.0）：`voice exec on|off` + `voice` 读回 `exec=0/1` 校准显示，解决「上电默认放行后没地方一键关闸」。
- **「后退」仍无实现**：需在步态层放开负速度（改 `motion_set_speed` 的 clamp 与 `execute_pending` 的 `speed>=0` 判断），单独一期悬空验，不能靠改命令词掩盖；语音词表第 2 条保持 `UNSUPPORTED`。

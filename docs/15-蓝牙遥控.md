# 15 · 蓝牙遥控（M3 落地）

让安卓手机通过 **BLE（低功耗蓝牙）** 直接控制机器狗，与原有的 Wi-Fi 网页控制台**并存**，两边都能发同一套命令。

> 给技术小白的类比：机器狗现在像一台「蓝牙音箱」——手机是「手机」，连上之后往里“说”命令（前进/左转…），它照做并把结果“回话”给你。Wi-Fi 网页控制台是另一台“遥控器”，同样能说话，互不冲突。

---

## 1. 架构一句话

```
手机 App  ──BLE写──▶  [CMD 特征值]  ──▶  cli_exec()  ──▶  机器狗动作
   ▲                                     ▲
   └─────── BLE通知 ◀── [STS 特征值] ◀───┘（执行结果回传）
```

关键点：**蓝牙、Wi-Fi 网页、电脑串口** 三端都调用同一个 `cli_exec()`，所以命令完全通用（`walk 50` / `left` / `stop` …）。新增蓝牙只是多了“一条嗓子”，狗脑子里的指令表没变。

ESP32-S3 **只支持 BLE，不支持经典蓝牙（SPP）**，所以手机必须用 BLE（GATT）方式连接，不能走老式蓝牙串口。

---

## 2. UUID 与特征值（手机 App 必须严格匹配）

固件 `main/ble_ctl.c` 里定义，App `BleConnection.kt` 里用同一组值：

| 项 | UUID |
|----|------|
| 设备名 | `Spider8` |
| 自定义服务 SVC | `4b9131c3-c9c5-cc8f-9e45-b51f01c2af4f` |
| CMD 特征值（手机**写**） | `4b9131c3-c9c5-cc8f-9e45-b51f02c2af4f` |
| STS 特征值（手机**读/订阅通知**） | `4b9131c3-c9c5-cc8f-9e45-b51f03c2af4f` |

> ⚠️ **UUID 字节序巨坑（2026-11-14 实测，耗了一整轮排查）**：本版 NimBLE 的 `BLE_UUID128_INIT` 宏是 `.value = { uuid128 }`、**不反转字节**，而 ATT 传输 128 位 UUID 走**小端**，导致“空中实际 UUID = 传入字节的反序”。所以 `ble_ctl.c` 里这三行必须写成**目标字符串的反序字节**（已写好并加注释），空中发出的 UUID 才与 App 的 `UUID.fromString()` 一致。若有人“好心”改成正序字节，板子会广播出反序 UUID（如 `4fafc201-…`），手机永远找不到服务。验证方法：本机跑 `python tools/gatt_probe.py` 直接扫，看 Service UUID 是否为上表三行。

- **CMD**：手机写 ASCII 命令，如 `walk 50`、`left`、`stop`。写回调只把命令塞进队列，**不阻塞**蓝牙栈，长命令（如脉宽扫描约 19s）也不会卡死连接。
- **STS**：板子执行完后把结果通过 notify 推回手机，App 在日志区显示。

## 3. 固件侧

### 3.1 新增/改动文件
- `main/ble_ctl.h` / `main/ble_ctl.c`：NimBLE GATT server：广播名 `Spider8`、暴露上述服务、命令桥接 `cli_exec()`、独立任务执行命令、结果分包 notify。
- `sdkconfig`：启用 `CONFIG_BT_ENABLED=y` / `CONFIG_BT_NIMBLE_ENABLED=y` / `CONFIG_BTDM_CTRL_MODE_BLE_ONLY=y`（Wi-Fi + BLE 共存）。**还必须有这两条，否则启动必崩**（见下方警示）：
  - `CONFIG_BT_NIMBLE_DYNAMIC_SERVICE=y` ← 关掉静态 GATT 服务数上限，改走堆分配
  - `CONFIG_BT_NIMBLE_MEM_ALLOC_MODE_EXTERNAL=y` ← NimBLE 堆改用 PSRAM

> ⚠️ **血泪坑（2026-11-14 实测）**：只开 `BT_NIMBLE_ENABLED` 编译通过、烧进去**一启动就崩**——日志反复打印
> `E NimBLE: ble_gatts_register_svcs rc=6`（= `BLE_HS_ENOMEM`）→ `assert ble_hs_event_start_stage2` → `Rebooting...` 无限重启循环。
> 根因是 **NimBLE 的静态 GATT 服务数上限**（`ble_hs_max_services` 固定数组）被我们加的这一个服务撑爆，跟堆内存无关。
> 把 `MEM_ALLOC_MODE` 切成 `EXTERNAL`(PSRAM) **无效**（那是堆不是计数上限）；**真正修复是开 `DYNAMIC_SERVICE`**，让 GATT 表改走堆分配（EXTERNAL 时落 PSRAM），不再受固定上限约束。
> 已验证可用固件：`build/spider8_ble_dyn_20261114.bin`（1,195,280B，广播名 `Spider8`，不崩）。
- `main/CMakeLists.txt`：`SRCS` 增加 `ble_ctl.c`，`PRIV_REQUIRES` 增加 `bt app_update`。
- `main/main.c`：`wireless_init()` 之后调用 `ble_ctl_init()`（失败仅告警，不致命）。

## 5. 烧录固件（必须！）

### 5.1 优先：Wi-Fi OTA（不用 USB 线）

板子连着家里路由时（IP 查 `http://192.168.0.102/api/net` 的 `sta_ip`，DHCP 会变），直接把原始 `.bin` POST 到 `/api/update`：固件自动写进空闲 OTA 槽，校验通过后 `esp_restart()` 重启生效。

```bash
curl -s -m 180 -X POST --data-binary @firmware/build/spider8.bin \
     -H "Expect:" -H "Content-Type: application/octet-stream" \
     http://192.168.0.102/api/update
```

⚠️ **`-H "Expect:"` 必须加**：curl 对 >1MB 的 body 会自动加 `Expect: 100-continue`，ESP-IDF 的 httpd 处理不好，body 收不全 → `esp_ota_end()` 报 `ESP_ERR_OTA_VALIDATE_FAILED`（旧固件保留、板子不坏）。实测 1.2MB 固件上传约 26 秒，成功返回 `OTA 成功接收 N 字节，马上重启进入新固件`。
- 连续 POST **两次**可让 `ota_0` / `ota_1` 两个槽都是同一版固件，避免以后回滚切回旧版。
- 第二次上传时板子可能在 curl 收到响应前就重启，`HTTP_CODE=000` 属正常；等 15 秒用 `/api/guard` 确认返回 `alive`。
- 验证新固件在跑：`/api/status` 的 `uptime` 变小说明刚重启；`/api/log` 是实时日志，能看到新版日志（如 `ble_ctl: BLE 回话 att_mtu=…`），无需串口。

### 5.2 兜底：USB 烧录

1. 板子**必须插标着 `USB` 的口**（VID_303A 原生 USB）；`UART` 口（CH340）本机驱动坏。
2. 电脑**退出 VPN**（LetsTUN 虚拟网卡会劫持路由）。
3. COM 号不固定，用 `tools/idf.ps1 -Port COMx flash` 指定。
4. 若 COM 口整个消失（连 `VID_303A` 设备都不见）＝ USB-Serial/JTAG 老毛病，**必须物理拔插 USB 线**，软件扫描救不回来。此时优先改走 5.1 的 Wi-Fi OTA。

`idf.py flash` 只写 `ota_0`。要两槽一致，另用 esptool 补写并清 otadata：

```bash
python -m esptool --port COMx --after no_reset write_flash 0x320000 firmware/build/spider8.bin
python -m esptool --port COMx --after no_reset erase_region 0x10000 0x2000
```

esptool 的 `Hard resetting via RTS` 在本板**不一定真复位**，需 DTR 脉冲强制 EN 复位后再验证（详见 §8）。

## 6. 手机安装与连接

1. 把 `app-debug.apk` 传到手机（微信文件传输/数据线/U 盘均可）。
2. 手机「设置 → 关于手机 → 连点版本号 7 次」开启开发者选项；在开发者选项里打开「USB 调试」和「允许安装未知来源应用」（或直接点 APK 时按提示授权）。
3. 点击 APK 安装（debug 包自带签名，无需上架应用商店）。
4. 打开 App → 点「连接 Spider8」→ 授权蓝牙/定位权限、开启蓝牙 → 自动扫描并连接。
5. 连接成功后按钮点亮，点「前进 / 左转 / 急停」即可；日志区能看到命令与狗的回话。

> 提示：BLE 只能在 App **前台**使用；切到后台再回来一般会自动重连（断线后 App 会重新扫描）。

## 8. 常见排错

| 现象 | 原因/对策 |
|------|-----------|
| App 搜不到 Spider8 | ① 板子没刷含 BLE 的新固件（最常见）；② 手机蓝牙没开；③ Android 6~11 没给定位权限；④ 距离太远/有干扰。先串口看板子有没有“BLE 初始化完成”日志。 |
| 连上了但按钮没反应 | 看 App 日志区有没有“→ walk 50 / → 已发送”；有发送但狗不动，按旧流程查舵机/电源（电池盒带载不足是历史头号坑）。 |
| 能发命令但收不到回话 | STS 通知开启失败；板子日志里 `ble_send_status` 应有 notify 发出，否则是 MTU/分包问题。 |
| 装 APK 提示“解析失败” | 手机 Android 版本 < 7（minSdk 24），或 APK 下载不完整（重传）。 |
| 板子连电脑烧录报 PermissionError(13) | 有别的程序占了 COM（Web Serial / 监视器 / 标定台），关掉再烧。 |
| **已连接，但日志“未找到 Spider8 自定义服务”随即断开** | **先查固件 UUID 字节序，再查 OTA 双槽，最后才查安卓缓存。** ① 首要嫌疑：`ble_ctl.c` 的 `BLE_UUID128_INIT` 字节序接反（本版 NimBLE 不反转、ATT 走小端 → 空中 UUID 成反序）。用本机 `python tools/gatt_probe.py` 扫，若服务 UUID 是 `4fafc201-…` 这类反序值就是这坑，把三处 UUID 字节反序即可。② 次嫌疑：分区表是双 OTA 槽，`idf.py flash` 只写 `ota_0`，而 `otadata` 指向的活动槽可能是 `ota_1`（旧示例固件）。用 esptool 把同一 bin 写 `0x20000` 和 `0x320000`、清 `otadata`(0x10000, 8KB)，再用 DTR 脉冲强制复位。③ 最后才是安卓 GATT 缓存：手机蓝牙「忽略/忘记 Spider8」再连。 |
| **能连上、能控制，几秒后自动断开** | **不要在「已连接」状态调用隐藏 API `BluetoothGatt.refresh()`**：多家厂商实现会重置 GATT 客户端状态，导致连接几秒后被断开（status 8/133）。曾为排查“找不到服务”把它加进 `onConnectionStateChange`，反而引入断连；真因（UUID 字节序）修好后已移除。现 App：连上后 `requestConnectionPriority(BALANCED)`、断连时打印 `status`（8=超时 / 133=栈异常 / 19=对端断开）、非主动断开自动重连最多 3 次。若**一发指令才断**，见下条 MTU 真因。 |
| **不发指令几分钟都稳，一发指令几秒后断 `status=8`** | **⭐ MTU 分包真因（2026-11-14 最终定位）**：固件 `ble_send_status()` 原用 `ble_att_preferred_mtu()-3`（本地【期望】值 253）分片，但安卓默认 ATT_MTU = **23**（净荷仅 20 字节）且不主动协商 → 发出超长 notify PDU，并把 `status` 命令近千字节输出分成几十片、撑爆 NimBLE msys mbuf 池（仅 36 块）→ 手机端链路监督超时 `status=8`。**只有发指令才产生 notify**，故「不发就稳、一发就断」；而电脑蓝牙自动协商大 MTU（本机 256），本机怎么测都正常，这个坑差点被本机测试放过去。修复三管齐下：① 固件改用 `ble_att_mtu(conn)` 取**实际** MTU，回话限长 512B / 限 32 片 / 片间 20ms；② App 连上主动 `requestMtu(256)`（`onMtuChanged` 打日志）；③ 断连打印 `status` + 自动重连。验证：板子日志 `BLE 回话 att_mtu=256 净荷=253B 实发=512B/总974 分3片`，发 `status` 后空闲 30s 不断，空闲后仍能写命令。⚠️ **但真机复测「MTU 协商成功：256 字节」后仍断，说明 MTU 不是唯一原因，见下一条。** |
| **MTU 已协商到 256，仍「不发指令稳、一发指令就 `status=8` 断」** | **2026-11-14 二轮定位：不是 MTU 分包，而是「板子疑似重启 + 连接参数太激进 + 安卓 GATT 并发」叠加。** ① 本机发 `walk 50`（舵机真动）25s 稳、回话仅 64B → 分包 / 运动任务抢占都不成立；② `tools/log_tail.py` 增量录 `/api/log?since=` 发现板子在**无人操作时自行重启过两次**（uptime 归零、日志序号回退），手机看到的「超时断开 → 板子重启后广播 → App 自动重连」很可能就是板子重启，必须查复位原因：`/api/status` 已加 `rst` / `brownout` 字段（`brownout=1`＝舵机启动把 5V 拉塌，属电源问题，换带载更强的电池盒，参 MEMORY「8 舵机全不动」坑）；③ 固件连上原请求 `itvl 12~24 / to=400`(4s) 太激进，Wi-Fi/BLE 共存丢几个连接事件就超时 → 改 `itvl 24~40 / to=1000`(10s)，本机实测 `参数更新结果 status=0 / 最终生效 itvl=36 to=1000`；④ App 连上同时发 `requestMtu` + `discoverServices` + `requestConnectionPriority`（GATT 并发 + 两端同时改参数）→ 改为 MTU 回调后再发现服务、移除手机侧参数请求、断连时 `gatt.close()`（防旧 client 占着 ACL 导致重连反复 8/133）；⑤ 回话收敛为**严格单包**（按实际 MTU 截断，任何 MTU 只发 1 条 notify），日志 `BLE 回话 … 单包`。 |
| 想留完整现场日志（板子重启会冲掉启动日志） | `python tools/log_tail.py ble_live_log.txt 3600`：每秒增量拉 `/api/log?since=`，带时间戳落盘；序号回退会明确记一行「板子重启」。这是区分「链路超时」与「掉压/崩溃重启」的关键证据，纯 HTTP、不占串口，可与手机 App 同时跑。 |
| **⭐ 最终真因：`status=8` 反复断连 + 自动重连，与 MTU / 指令 / 舵机都无关** | **`wireless.c` 的「网页服务自愈看门狗」在遥控途中把板子重启了。** 它每 5 秒从板子内部连自己的 80 端口做自检，APSTA 连上家里路由后这个内部连接会**持续误判失败**（外部 `curl /api/guard` 明明回 `alive`）；原阈值 `GUARD_FAIL_LIMIT=8`（约 40 秒）一到就 `esp_restart()` → **板子每约 70 秒自杀式重启一次**。手机自然「超时 status=8 断连 → 板子重启后重新广播 → App 自动连回」。`tools/log_tail.py` 完整录到 `网页服务自检失败 1/8 … 7/8` 紧接着 `板子重启`，铁证。**根治**：① 新增 `ble_ctl_is_connected()`，`httpd_guard_task` 在 **BLE 连接期间直接跳过自动重启**（`fails=0; continue;`）——遥控时绝不自作主张重启；② 阈值 8→60（5 分钟）、probe 超时 1.5s→3s，减少无 BLE 时的误重启；③ `/api/status` 加 `rst`/`brownout` 字段排除掉压。固件 `build/spider8_ble_guard_20261114.bin`=1,197,392B。**验证**：OTA 刷入后本机蓝牙模拟遥控 90s，`uptime` 从 19 连续涨到 120（未归零）、90s 不断、空闲后仍能写命令，自检失败累到 `17/60` 板子也不重启。 |
> 遗留优化（不影响使用）：自检在 APSTA 模式下仍会误判并持续打 `自检失败 x/60` 警告。将来可把 `guard_probe()` 的目标地址改为先试 `127.0.0.1` 再试 STA IP，消除误判。当前因阈值放宽 + BLE 期间禁止重启，已无实际危害。

## 9. 2026-11-14 第四轮：长时间后偶发断连 + App 双页面改版

用户反馈「比上次好很多，基本不断了，但时间长了还是会断」，同时要求 UI 对齐 `console.html`、增加 trim 标定页。本轮三个根因 / 改动分组如下。

### 9.1 残留断连的两个真因

| # | 真因 | 证据 | 修法 |
|---|------|------|------|
| A | **手机把连接参数压成 `itvl=6 / to=500`**（7.5ms 间隔、监督超时仅 5s）。安卓在 GATT 操作期间自动请求 HIGH，旧 `CONN_UPDATE_REQ` 只打日志就接受，等于把 5s 超时放进来；Wi-Fi/BLE 共用 2.4GHz，路由器一忙连丢几个事件 → `status=8`。短时间看不出，放久了必现。 | `/api/log` 实录：`BLE 手机请求连接参数` → `最终生效 itvl=6 lat=0 to=500`，随后又回到 `itvl=24 lat=2 to=2000`，来回拉锯 | `ble_ctl.c` 新增 `clamp_conn_params()`：在 `CONN_UPDATE_REQ` 回填 `self_params`、在 `L2CAP_UPDATE_REQ` 就地夹紧 `peer_params`（本版 NimBLE 该路径 `self_params` 为 NULL，host 会直接拿它去 `ble_gap_update_params`），把下限钉在 30~50ms / 20s；`CONN_UPDATE` 完成后若仍检测到危险参数，最多再申请 3 次安全参数 |
| B | **网页自检探针自己写错**：只读 HTTP 响应前 64 字节，那一段全是响应头，正文 `alive` 根本没读到 → **无论连哪个地址都必然判失败**。这才是「每 5 秒刷一条自检失败」的源头（之前误判成 APSTA 绕路误判），也是历史上 `esp_restart()` 反复触发的深层原因 | 外部 `curl /api/guard` 明明回 `alive`；板子日志却每 5s 一条 `自检失败 x/60` | `wireless.c` 的 `guard_probe_addr()` 循环 recv 到出现 `alive` 为止（512B 缓冲）；依次试 `127.0.0.1` → AP 地址 → STA 地址；BLE 连接期间**整个探针都跳过**（不再制造 2.4G 射频活动）；**彻底删除 `esp_restart()`**，网页服务异常只记日志（重启必断蓝牙，取舍明确）；日志降为每 60 次才一条 |

配套：`ble_gap_update_params` 的连上默认参数统一为 `itvl 24~40 / latency 2 / supervision_timeout 2000`（20s）。本机 `uptime` 连续 533s 未归零、`rst=3`（软件重启，非 panic / brownout）、`brownout=0`。

### 9.2 新增固件命令 `trimget <0-7>`

BLE 回话是**严格单包**（按实际 ATT_MTU 截断），而 `status` 的 8 路表格近千字节，手机永远只能收到开头几行，拿不到 trim/dir。`trimget` 一次只读一路，回显 `T0=-30.0/1`（约 13B），任何 MTU 都塞得下。App 标定页依次发 `trimget 0..7` 取回全表，不用改 BLE 分包逻辑。已注册进 `console.c` 的同一张命令表，串口 / 网页 / 蓝牙都能用。

### 9.3 安卓 App

- **BleBus 单例**：遥控页与标定页共用同一条 GATT 连接，切 Activity 不断线；监听器支持多路，新页面只给自己补发历史日志（不用 `dispatch`，否则旧页面会重复一整份日志）。
- **写命令串行队列**：安卓 GATT 同时只允许一个未完成写操作，以前拖滑块 / 连发 8 条 `trimget` 会静默丢命令；现在等 `onCharacteristicWrite` 再发下一条，带 2.5s 超时兜底，连接前缓存的命令在 `onServicesDiscovered` 补发。
- **自动重连**：非主动断开改成无限退避（1.5/3/5/8s，连上清零），加 15s 扫描超时。
- **主页 UI** 对齐 `console.html`：同一套绿 `#0F6E56` / 红 `#D93025` 配色与卡片式布局；按钮集合与 `data-cmd` 逐字一致（急停、站立/蹲下/趴下/握手/挥手/连续演示、波步前进/小跑/后退/左转/右转/回正直行/停止站定、`status`/`pcadiag`/`pwm off`/`cal off`），速度·转向·周期·步幅·抬脚·占空比 6 个滑块松手才发命令。
- **新增 `CalibActivity`**（对应 `tools/servo_calib.html` ①~⑥）：8 通道选择、±0.5°/±1°/归零、−50~+50° 滑块（120ms 节流并保证最后一次发出）、站姿舵机角推算、安全翻转 dir（先 `pwm off`→`cal off`→`pose stand`→等 700ms）、读取 8 路 / 保存 / 只归零 trim / 全清 / 通电自检 / 退出 raw 模式、命令终端。
